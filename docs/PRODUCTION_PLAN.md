## 3. วิธีผลิตโมเดล

ใช้ polygon control cages ที่จัดรูปทรงและระนาบแยกแต่ละตัว เก็บจุดยอด/หน้า polygon ที่สร้างแล้วใน `art/meshes/*.mesh.json` และปรับจุดยอดผ่านเว็บได้ Three.js ใช้แสดงโมเดลจริงและส่งออก GLB โดย build ปกติรักษา JSON เดิม การเปลี่ยนนามสกุลไฟล์ไม่ได้ทำให้โมเดลสวยขึ้น จึงตรวจจากภาพจริงและแก้สัดส่วนทุกขั้น

เริ่มจาก box modeling / extrusion / mirror เพื่อจัดมวลหลัก จากนั้นปรับ topology รอบตา แก้ม ปาก หู และข้อต่อให้เหมาะกับการแสดงสีหน้าและเคลื่อนไหว รูปทรงที่ต่อกันต้องอ่านเป็นสัตว์ตัวเดียว พื้นผิว low-poly เกิดจากการจัดระนาบอย่างตั้งใจ ไม่ใช่ลดจำนวน polygon แบบสุ่มแล้วรับผลทันที

งานอัตโนมัติใช้สร้าง scene, ตั้งกล้อง, ทำชื่อวัตถุ, batch render, export และตรวจข้อมูลได้ ส่วนสัดส่วน ความน่ารัก ตำแหน่งตา รูปแก้ม และจังหวะระนาบ ต้องวนแก้จากภาพจริงของ mesh

## 4. ลำดับงานและสิ่งที่ต้องส่งให้ตรวจ

### M0 — เตรียมแหล่งอ้างอิงและพิสูจน์เครื่องมือ

1. นำภาพต้นฉบับทั้งสองไฟล์เข้า `references/original/` บนเครื่องปั้น และตรวจ SHA-256 ให้ตรง manifest โดยคงไฟล์เดิมครบถ้วน
2. ตั้งภาพอ้างอิงและกำหนดกล้องหลักของแต่ละตัว แยกมุมที่เห็นจริงกับมุมที่ต้องตีความขึ้นใหม่
3. Trace จุดสำคัญ ได้แก่ ปลาย/โคนหู ขอบแก้ม หัวตา-หางตา จมูก คาง อก ขอบอุ้งเท้า และโคน/ปลายหาง ตัวเลขสัดส่วนให้วัดจากมุมเดียวกันและระบุว่าเป็นค่าจากภาพฉาย
4. ตรึง Three.js 0.185.1 และเครื่องมือ build ตรวจ module loading, การแก้ mesh JSON และ GLTFExporter
5. พิสูจน์ pipeline: mesh JSON → render PNG → export GLB → เปิด GLB กลับใน scene ใหม่ ตรวจ normal และรูปทรง; แยกผลเทคนิคจากการอนุมัติศิลป์
6. บันทึกกล้อง แสง พื้นหลัง exposure และขนาดภาพเป็น review stage กลาง

**ผลที่ต้องได้:** ต้นแบบบนเครื่องปั้นพร้อม hash, scene สำหรับตรวจงาน, รายงานว่า save/render/export/viewer ทำงานจริง

**สถานะปัจจุบัน:** นำไฟล์ต้นฉบับเข้าเครื่อง B แล้ว; build, mesh validation, การแก้/undo/โหลด JSON, GLB export/re-import และ viewport มือถือผ่านการทดสอบ รายงานอยู่ใน `review/M1/report.json` ยังไม่ได้ทดสอบโทรศัพท์จริง

### M1 — ขึ้นโครงสีเทา: Jew ก่อน

ปั้นมวลใหญ่โดยยังไม่ใช้สีขนมาช่วยความเหมือน:

1. หัวกว้างและแก้มอิ่ม กะโหลกมีระนาบหน้าผากลงสู่จมูก ปากสั้น คางกระชับ
2. หูสามเหลี่ยมมีความหนาและโคนหูเชื่อมกับกะโหลก
3. อก ลำตัว และสะโพกกะทัดรัด คอไม่ยืดยาว ขามีน้ำหนัก อุ้งเท้ากว้าง
4. หางมีโคนต่อเนื่องและค่อย ๆ เรียว ท่านั่งและท่าเดินใช้ตัวละครเดียวกัน
5. จัดเบ้าตาและตำแหน่งจมูกในระดับโครงสร้าง เพื่อเห็นปัญหาหน้าตั้งแต่ต้น

ฉบับ M1 ปัจจุบันเป็นโครง SIT สำหรับตรวจมวลและใบหน้า ยังไม่ใช่ mesh ที่พิสูจน์การเดินหรือ skinning แล้ว หลังรับทิศทางรูปทรงให้สร้าง neutral stand และจัด topology สำหรับ rig โดยรักษาหัว/ใบหน้าที่ผ่าน ทั้งสอง artist ทำงานคู่ขนานบน source แยกกันและใช้ anatomy ของลูกโกลเด้นแยกจาก Jew

**ชุดตรวจ:** mesh JSON และ GLB จริง, ภาพเทียบมุมต้นแบบ, หน้า/ข้าง/หลัง/สามส่วนสี่, silhouette และ turntable สั้น ทั้งหมดมาจากไฟล์เดียวกัน

**ผ่านเมื่อ:** สัดส่วนหัว แก้ม หู ปาก อก อุ้งเท้า และหางตรงทิศทางภาพ แม้ยังไม่มีสี; ตัวละครอ่านออกจาก silhouette; จุดต่อไม่ดูเป็นวัตถุหลายชิ้นเสียบกัน ให้ผู้ใช้ตรวจโครงทรงก่อนผ่านช่วงนี้

### M2 — ใบหน้า ระนาบ และความพร้อมแสดงสีหน้า

**Jew:** ทำเบ้าตาที่รับกับผิวหน้า เปลือกตาหุ้มลูกตาและสามารถหรี่ตาจริง รักษาแก้มกว้าง ปากสั้น จมูกเล็ก และขอบตาแบบ almond ตาม SQUINT ความซนเกิดจากระดับเปลือกตา สายตา และความไม่สมมาตรเล็กน้อย

**Bo:** ทำหัวลูกหมาที่กว้างและโค้ง ปากสั้นกว้าง หูตกเป็นแผ่นมีความหนาข้างแก้ม ตาฝังอยู่ในใบหน้า ปากปิดผ่อนคลายตามภาพ ไม่เพิ่มรอยยิ้มกว้างหรือลิ้นยื่นในแบบหลัก

จัดระนาบใหญ่บริเวณหน้าผาก แก้ม อก และสะโพก ส่วนรอบตาและปากมี topology เพียงพอสำหรับ deformations ทดลองช่วงการเคลื่อนไหวของเปลือกตาก่อนตรึง topology แล้วจึงสร้าง shape keys ให้ครบ

**ชุดตรวจ:** ภาพหัวใกล้จากมุมต้นแบบและด้านข้าง, wireframe, faceted gray render; Jew SQUINT / SIDE-EYE / CHEEKY และ blink ทดสอบ; Bo ใบหน้าหลักและ blink ทดสอบ ใช้สีพื้นเรียบในตาเป็น diagnostic ได้โดยระบุให้ชัด

**ผ่านเมื่อ:** บุคลิกตรงภาพ ตาไม่โปนหรือเป็นแผ่นลอย หนังตาไม่ทะลุ ลูกตาไม่ถูกย่อแบนเพื่อแกล้งเป็นการหรี่ตา และการเปลี่ยนสีหน้าไม่ทำให้โครงหน้ากลายเป็นคนละตัว ผู้ใช้ตรวจใบหน้าก่อนงานสีเต็มรูปแบบ

### M3 — สี วัสดุ และแสง

ลงสีบนรูปทรงที่ผ่านแล้ว:

- Jew: ขนดำสม่ำเสมอ ตาอำพัน รูม่านตาเข้ม จมูกและหูชมพูหม่นตามภาพ ใช้แสงให้เห็นระนาบโดยยังอ่านเป็นแมวดำ
- Bo: ขนทองอุ่น ปาก อก และปลายเท้าครีม ตาและจมูกน้ำตาลเข้ม คุมขอบเขตสีตามภาพ แยก highlight ออกจากลายขนก่อนลงสีถาวร
- ผิวลำตัว matte/soft satin และผิวตาเรียบกว่า มี catchlight เล็ก ๆ ไม่ใช้สีทองแบบโลหะหรือความมันวาวทั่วตัว
- ใช้วัสดุ PBR ที่ส่งออก GLB ได้เป็นฐาน และตรวจว่าสีหน้าผาก/ปลายหางของ Bo เป็น marking หรือผลจากแสง หากภาพไม่ชัดให้แสดงทางเลือกใน marking map ของโมเดล

**ชุดตรวจ:** ภาพสีจากกล้องเดิมเทียบต้นแบบ, มุมรอบตัว, swatch/marking map, Jew บนพื้นหลังกลางและ dark mode, Bo บนพื้นหลังกลางและ light mode

**ผ่านเมื่อ:** สีตรงบุคลิกและภาพ โดย silhouette และหน้าที่ผ่านแล้วไม่เปลี่ยน ผู้ใช้ตรวจภาพโมเดลจริงหลังลงสี

### M4 — Rig และพิสูจน์ GLB ระยะแรก

สร้าง skeleton สำหรับ spine/neck/head, ขาสี่ข้าง, หูและหางตามความจำเป็น ทำ skin weights บริเวณไหล่ ศอก สะโพก เข่า คอ และโคนหาง จากนั้นตรวจ stand, sit, ยกเท้า และเดินหนึ่งก้าว รวมถึงเปลือกตา

ส่งออก GLB ทดสอบที่มีวัสดุ blink และหนึ่งก้าวทันที เพื่อพบข้อจำกัดของ exporter ก่อนสร้าง animation ทั้งชุด เปรียบเทียบ mesh, normals, faceting, สี, eyes, skinning, morph targets, scale และแกนพิกัดใน viewer จริง

**ผ่านเมื่อ:** จังหวะงอไม่ยุบหรือทะลุ ฝ่าเท้ารับพื้น เปลือกตาปิดได้จริง และ exported GLB รักษาหน้าตา/รูปทรงของไฟล์ต้นฉบับ หากแก้ topology แล้วกระทบหน้าหรือ silhouette ต้องส่งภาพส่วนที่เปลี่ยนให้ตรวจใหม่

### M5 — Animation และบุคลิกเต็มชุด

ทำ clip ตามลำดับ: idle/stand → sit → walk → blink/gaze → head tilt → stretch/sleep → paw/groom → carry/drop → dig/heart reveal → Jew nibble

ท่านั่ง เดิน และสีหน้าต้องมาจาก mesh/rig เดียวกัน คุมเท้าไม่ลื่น การแกว่งหู/หางไม่แรงจนเปลี่ยนบุคลิก และ blend ระหว่างท่าไม่กระชาก กำหนดผู้ควบคุมกระดูกแต่ละชุดให้ชัด ไม่ให้ clip กับ procedural adjustment แย่งเขียนกระดูกเดียวกัน

Jew กัดเบา ๆ แล้วหลุดเมื่อถูกลากนานตาม product requirement; Bo ถูกอุ้มได้นานโดยไม่บังคับปล่อย ทั้งคู่ไม่ไล่โจมตีเคอร์เซอร์เอง

**ชุดตรวจ:** คลิปสั้นของท่าหลักและ transition ที่เสี่ยง, contact sheet, GLB motion preview ที่ระบุไฟล์จริง

### M6 — เว็บขั้นต่ำและการตรวจบนมือถือ

สร้างระบบใหม่สำหรับโหลด asset ที่ผ่านแล้ว พร้อม interaction ตามบรีฟ: dark mode แสดง Jew, light mode แสดง Bo, แตะ/ลูบ/ลาก, pointer cancel, ปล่อยมือขอบจอ, เปลี่ยนธีมระหว่างอุ้ม, ขุดพบกระดาษหัวใจ และข้อความให้กำลังใจ

ใช้ viewer สำหรับตรวจภาพก่อนสร้างหน้าแอปเต็ม เปรียบเทียบ source mesh render กับ GLB ที่เปิดกลับด้วยกล้อง ท่า แสง และขนาดใกล้กัน แยกข้อแตกต่างของ renderer ออกจากข้อผิดพลาดของ export

ตรวจที่ความกว้าง 320, 390 และ 430 px รวม landscape และ desktop 900×900 ตรวจ Safari/WebKit และ Chrome พร้อมโทรศัพท์จริงที่ระบุรุ่นได้ การทดสอบ emulator ต้องรายงานตามจริง

งบประสิทธิภาพตั้งหลังมีโมเดลที่ผ่านด้านภาพแล้ว วัด exported vertices/triangles, draw calls, bytes, memory และ frame time ของฉากจริง ตั้งต้นด้วยสัตว์ที่ active หนึ่งตัวและวัสดุเท่าที่จำเป็น เป้าหมายเบื้องต้น 30 FPS ต่อเนื่องบนเครื่องตัวแทนและ 60 FPS เมื่อไหว เป็นเป้าหมายเพื่อวัด ไม่ใช่ผลที่ผ่านแล้ว ปรับสิ่งที่ไม่เปลี่ยนรูปลักษณ์ก่อนลดรายละเอียดหน้าและ silhouette

### M7 — ตรวจรับและเตรียม release

ตรวจเทียบภาพต้นฉบับรอบสุดท้ายพร้อมผลทดสอบ interaction/export/mobile ระบุ source และ GLB hash ที่ส่งจริง การเปลี่ยน geometry/material หลังอนุมัติต้องมีภาพเปรียบเทียบ ไม่ใช้ภาพเก่ามายืนยันไฟล์ใหม่

จัด release ที่ตรวจได้ แล้วจึงดำเนินการ commit/push/deploy ตามขอบเขตของขั้น release ไม่มีการส่งเว็บว่างหรือโครงทดลองขึ้น production ระหว่างการล้างและวางแผน

## 5. การจัด agent

รอบวางแผนนี้ใช้ 3 agent: วิเคราะห์ภาพโดยไม่อ่านโมเดลเดิม, ค้นแหล่งวิธีปั้นจากผู้สร้าง/เอกสารทางการ และตรวจแผนผลิต/ความเสี่ยง โดย supervisor รวบรวมผลและทำการล้างโปรเจกต์

| บทบาทในช่วงผลิต | งานที่รับผิดชอบ | ทำคู่ขนานได้เมื่อ |
| --- | --- | --- |
| Supervisor / Art Director | กำกับบรีฟ ลำดับงาน และสถานะการตรวจรับ | ตลอดงาน |
| Reference Analyst | ภาพหลัก landmarks และมุมที่ต้องตีความ | คู่กับเตรียมเครื่องมือ |
| Pipeline Engineer | mesh build, review stage, export และ manifest | คู่กับวิเคราะห์ภาพ/ปั้น โดยไม่แก้ mesh ของ artist |
| Jew Artist | ไฟล์ master ของ Jew รวมการส่งต่องาน rig | หลัง M0 |
| Bo Artist | ไฟล์ master ของ Bo รวมการส่งต่องาน rig | หลัง stage กลางและทิศทาง blockout พร้อม |
| Visual QA | ตรวจภาพและเขียนข้อแก้แยกจากผู้ปั้น | หลังมีภาพจากไฟล์จริง |
| Web Engineer | viewer แล้วจึงระบบ interaction | viewer เมื่อ GLB ทดสอบแรกส่งออกได้ภายใน M0; แอปหลัง asset ผ่าน |

หนึ่งไฟล์ master มีผู้เขียนคนเดียวเสมอ งาน rig/material อาจส่งต่อให้ผู้เชี่ยวชาญโดยย้าย ownership อย่างชัดเจน ห้ามหลาย agent เขียน source/mesh JSON ตัวเดียวพร้อมกัน ทุก handoff ระบุ starting hash, stage, owner, paths และสิ่งส่งมอบ QA เสนอผลตรวจได้แต่ไม่บันทึกว่าเจ้าของงานอนุมัติแทนผู้ใช้

## 6. โครงสร้างปลายทางที่เสนอ

| ตำแหน่ง | หน้าที่ |
| --- | --- |
| `references/original/` | ภาพต้นฉบับไม่ดัดแปลง |
| `references/measurements/` | landmarks และสิ่งที่สังเกต/อนุมานจากภาพ |
| `web/studio.js` | กล้อง แสง และ renderer สำหรับตรวจงาน |
| `art/source/jew.mjs` + `art/meshes/jew.mesh.json` | control cage และต้นฉบับจุดยอด Jew |
| `art/source/bo.mjs` + `art/meshes/bo.mesh.json` | control cage และต้นฉบับจุดยอด Bo |
| `scripts/` + `tests/` | build/render/export/validation ที่ใช้จริง |
| `review/M1/` | ภาพ GLB manifest และผลตรวจของ revision ล่าสุด |
| `exports/` | GLB ที่ผ่านการตรวจและ asset manifest |
| `web/` | เว็บใหม่ที่โหลดโมเดลสำเร็จรูป |

โครงสร้าง M1 สร้างแล้ว ส่วน rig, animation และ final exports ยังเป็นแผน ไฟล์อ้างอิง/ภาพตรวจ/GLB ระยะแรกมีขนาดเล็กและเก็บใน Git ปกติ; หาก asset โตขึ้นให้เลือก binary storage ก่อนเพิ่ม

## 7. เกณฑ์คุณภาพที่ห้ามข้าม

1. โครงสีเทาต้องผ่านก่อนใช้สีและแสงแต่งเต็มรูปแบบ
2. Jew มีใบหน้าหรี่ตาซนตาม MISCHIEF STUDY; Bo มีหัว/ปาก/หูแบบลูกโกลเด้นตาม CONCEPT 01
3. ทุกภาพที่อ้างว่าเป็นโมเดลต้อง render จาก mesh JSON หรือ GLB ที่ระบุ hash ได้
4. การนั่ง เดิน หันหน้า และแสดงสีหน้าต้องไม่เปลี่ยนตัวตนของโมเดล
5. ผิว faceted ต้องมีระนาบสวย และ silhouette อ่านง่ายทั้งมุมใกล้กับขนาดที่แสดงบนมือถือ
6. มุมที่ภาพต้นฉบับไม่ระบุให้เสนออย่างเปิดเผยและแสดงใน turntable
7. ผ่าน build/test เป็นหลักฐานด้านเทคนิค ส่วนความเหมือนต้องตรวจภาพจริงแยกกัน

## 8. งานถัดไปที่ควรเริ่ม
